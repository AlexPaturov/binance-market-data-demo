# Binance Data Collector 

**Binance Data Collector** — это автономный, самовосстанавливающийся и отказоустойчивый программный комплекс, предназначенный для непрерывного сбора и хранения рыночных данных с криптовалютной биржи Binance.

Система построена на .NET 8, PostgreSQL и Docker, с полностью автоматизированным процессом развертывания (CI/CD) через GitHub Actions.

## ✨ Ключевые возможности

- **Динамический выбор пар:** Автоматически определяет и отслеживает самые ликвидные и волатильные валютные пары.
- **Сбор тиковых данных:** Собирает данные о каждой сделке в реальном времени через WebSocket.
- **Агрегация свечей:** Автоматически агрегирует тиковые данные в 1-минутные свечи (OHLCV).
- **Самовосстановление:** Встроенный аудитор находит и заполняет пробелы в данных, возникшие из-за простоев.
- **Автоматическое развертывание:** Любые изменения в `master` ветке автоматически собираются, тестируются и развертываются на сервере.
- **Кросс-платформенность:** Благодаря Docker, система может быть развернута на любой ОС, поддерживающей контейнеры. 

> **Текущий режим — начальная загрузка истории.** Сейчас идёт однократная заливка годового исторического массива (~1 ТБ архивов Binance). На это время периодические расчёты (агрегация OHLCV, расчёт признаков, аудиторы пропусков) и realtime-сбор через WebSocket временно приостановлены, чтобы отдать дисковый I/O массовой распаковке и вставке. После завершения загрузки выставляются watermarks, и все периодические процессы включаются в штатную работу.

## 🚀 Технологический стек

- **Бэкенд:** C# / .NET 8
- **База данных:** PostgreSQL 16 (+ PgBouncer)
- **Брокер сообщений:** RabbitMQ
- **Фоновые задачи:** Hangfire (отдельная БД `market_analytics_jobs`)
- **Логи:** Seq (централизованный сбор через Serilog)
- **Среда выполнения:** Docker / Docker Compose
- **CI/CD:** GitHub Actions (Self-hosted Runner) + GHCR
- **Основная ОС сервера:** Ubuntu Server 22.04 LTS

**Только в PROD:**

- **Reverse proxy:** Traefik (TLS-терминация, маршрутизация)
- **Внешний доступ:** Cloudflare Tunnel (без проброса портов)
- **Мониторинг:** Uptime Kuma

## 🗄️ Схема базы данных

Схема воспроизводится из репозитория одной командой. Каталог `docker/postgres/init/` монтируется в `docker-entrypoint-initdb.d` контейнера PostgreSQL и на **чистом томе** применяется автоматически при первом старте:

- `01_create_jobs_db.sql` — создаёт служебную базу Hangfire `market_analytics_jobs`.
- `02_schema.sql` — полная схема основной БД `market_analytics` (таблицы `Trades`, `Ohlcv_1min`, `Ohlcv_Features`, `TrackedSymbols`, `Processing_Watermarks`, `HistoricalAudit_Watermarks` и функции обработки). Это schema-only снимок (`pg_dump`) актуального прод-состояния.

Тем самым `./docker/dev-start.sh` на пустом томе поднимает готовую к работе БД без ручных шагов. Подробное описание модели данных — **[docs/common/03_database.md](./docs/common/03_database.md)**.

## 🔧 Установка и запуск

### 1. Локальная разработка

Инфраструктура (PostgreSQL, PgBouncer, RabbitMQ, Seq) поднимается в Docker на локальной машине одной командой:

```bash
./docker/dev-start.sh   # поднять инфраструктуру
./docker/dev-stop.sh    # остановить
```

На чистом томе PostgreSQL схема БД и служебная база Hangfire создаются автоматически из `docker/postgres/init/` (см. «Схема базы данных» ниже). Worker и DataManager запускаются из IDE (или `dotnet run`) как обычные .NET-процессы и подключаются к локальной инфраструктуре.

Полная инструкция и схема — **[docs/dev/ARCHITECTURE_DEV.md](./docs/dev/ARCHITECTURE_DEV.md)**.

### 2. Развертывание на сервере

CI/CD построен на GitHub Actions. Каждый `push` и Pull Request в `master` проходит job `build-and-test` (сборка, тесты и publish обоих приложений на `ubuntu-latest`). Развёртывание (`deploy`) выполняется на self-hosted runner **только** при push в `master` или ручном запуске (`workflow_dispatch`) и не запускается на Pull Request: собирает образы, пушит их в GHCR (аутентификация через встроенный `GITHUB_TOKEN`) и перезапускает прод через `docker compose`.

Подробности — **[docs/prod/04_deployment.md](./docs/prod/04_deployment.md)**.

## ▶️ Демо-сценарий (локально)

Минимальный воспроизводимый сценарий на локальной машине:

1. **Поднять инфраструктуру:** `./docker/dev-start.sh`. На чистом томе PostgreSQL автоматически применяется схема (`02_schema.sql`) и создаётся база Hangfire `market_analytics_jobs`.
2. **Запустить приложения:** Worker и DataManager из IDE (или `dotnet run`).
3. **Открыть DataManager:** `http://localhost:7002`, войти через Azure B2C. Доступ разграничен ролями `Viewer` / `Operator` / `Admin`.
4. **Обновить список пар:** на странице Archives (роль `Operator`) — «Обновить символы»; задача уходит в очередь Hangfire, таблица `TrackedSymbols` наполняется активными парами.
5. **Импортировать архив:** там же выбрать пару и диапазон дат → скачать дневные архивы Binance → обработать (распаковка + bulk-insert). Сделки появляются в таблице `Trades`.
6. **Посмотреть результат:** сводка по БД на главной DataManager или прямой SQL-запрос к `Trades`.
7. **Дальше по пайплайну:** агрегация в `Ohlcv_1min` и расчёт признаков в `Ohlcv_Features` выполняются периодическими джобами Worker в штатном режиме (на время начальной загрузки они приостановлены — см. «Текущий режим»).
8. **Hangfire-дашборд:** `http://localhost:7002/hangfire` (роль `Admin`) — состояние очередей и задач; отсюда же вручную запускается проверка качества данных (`DataQualityWorker`).
