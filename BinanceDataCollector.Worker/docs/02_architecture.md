# Документация: 02 - Архитектура приложения

Этот документ описывает высокоуровневую архитектуру системы `BinanceDataCollector`, взаимодействие ее компонентов и ожидаемое поведение в штатном режиме.

## 1. Архитектурный подход

Система построена на **микро-воркерной архитектуре** на базе .NET `BackgroundService`. Все приложение работает как единый процесс, но внутри него параллельно и независимо функционируют четыре "воркера", каждый из которых отвечает за свою, четко определенную задачу.

Такой подход обеспечивает:
- **Разделение ответственности (Separation of Concerns):** Каждый воркер легко понять, протестировать и модифицировать, не затрагивая остальные.
- **Отказоустойчивость:** Сбой в одном из второстепенных воркеров (например, в Аудиторе) не остановит основной процесс сбора данных.
- **Масштабируемость:** В будущем любой из воркеров может быть вынесен в отдельный микросервис, если его нагрузка возрастет.

Вся система, включая базу данных, упакована в **Docker-контейнеры** и управляется через `docker-compose`, что гарантирует идентичность окружения при разработке и на "боевом" сервере.

## 2. Описание узлов (воркеров)

Система состоит из четырех независимых фоновых служб, работающих параллельно.

### 2.1. `SymbolUpdateWorker` (Сканер/Менеджер)

- **Задача:** Определять, **ЧТО** мы собираем.
- **Триггер:** Запускается по расписанию (например, раз в 24 часа).
- **Взаимодействие:**
  - Обращается к `MarketScreener` для получения списка ТОП-N активных пар с Binance.
  - Обращается к `ITrackedSymbolRepository`, чтобы обновить этот список в таблице `"TrackedSymbols"` в базе данных (выставляет флаги `"IsActive"`).
- **Поведение при сбое:** Если не удается получить данные с Binance, он логирует ошибку и пропускает текущий цикл. Система продолжит работать со старым списком активных пар.

### 2.2. `BinanceTradesWorker` (Сборщик/Диспетчер)

- **Задача:** Управлять процессом сбора данных в реальном времени.
- **Триггер:** Запускается при старте приложения и периодически (например, раз в час) проверяет актуальность задач.
- **Взаимодействие:**
  - Обращается к `ITrackedSymbolRepository`, чтобы получить **текущий** список активных пар из базы данных.
  - Сравнивает полученный список с уже запущенными задачами.
  - Запускает новые задачи сбора (`DataSyncService`) для новых пар.
  - Останавливает задачи для пар, которые перестали быть активными.
- **Поведение при сбое:** Ошибки в дочерних задачах (`DataSyncService`) на него не влияют. При "холодном старте" (пустая база) терпеливо ждет, пока `SymbolUpdateWorker` наполнит базу данными.

### 2.3. `OhlcvAggregatorWorker` (Агрегатор)

- **Задача:** Превращать сырые данные в полезную информацию (тиковые данные → свечи).
- **Триггер:** Запускается по расписанию (каждую минуту).
- **Взаимодействие:**
  - Вызывает метод `ExecuteAggregationAsync` в `ITradeRepository`.
  - Этот метод, в свою очередь, запускает на сервере базы данных функцию `sp_aggregate_trades_to_ohlcv`. Вся "тяжелая" работа по агрегации происходит на стороне СУБД.
- **Поведение при сбое:** При ошибке SQL логирует ее и пропускает текущий цикл, не "роняя" приложение. Блокировка (`SemaphoreSlim`) предотвращает конфликты при "зависших" или долгих запусках.

### 2.4. `DataAuditorWorker` (Ревизор)

- **Задача:** Гарантировать историческую полноту данных.
- **Триггер:** Запускается по расписанию (например, раз в 2 часа).
- **Взаимодействие:**
  - Получает список активных пар из `ITrackedSymbolRepository`.
  - Для каждой пары проверяет последнюю запись через `GetLastTradeTimeAsync` в `ITradeRepository`.
  - При обнаружении "дыры" скачивает недостающие данные через `GetHistoricalAggTradesAsync` в `IBinanceService` и сохраняет их через `BulkInsertAsync`.
- **Поведение при сбое:** Ошибка при обработке одной пары не влияет на другие. При больших разрывах (>24 часа) он не пытается его заполнить, а пишет критическое сообщение в лог, сигнализируя о необходимости ручного вмешательства.
  > `[CRITICAL] Требуется ручное вмешательство: обнаружен разрыв >24h для пары {symbol}`

## 4. Ожидаемый результат при правильной работе

При штатной работе системы вы будете наблюдать следующую картину:

### 4.1. Логи приложения
- **Постоянный поток сообщений** от `DataSyncService`:
  > `[BTCUSDT] Сохраняем 25 сделок...`
- **Периодические сообщения** от других воркеров:
  - **Каждую минуту:** `Агрегация свечей завершена.`
  - **Каждый час:** `Проверка завершена. Активно отслеживается 40 пар.`
  - **Каждые 2 часа:** `[ETHUSDT] Проверка пройдена. Дыр в данных не обнаружено.`
  - **Каждые 24 часа:** `Начинаем плановое сканирование рынка... База данных отслеживаемых символов успешно обновлена.`

### 4.2. Состояние базы данных
- **Таблица `"Trades"`:** Постоянно и быстро растет.
- **Таблица `"Ohlcv_1min"`:** Каждую минуту пополняется новыми, полностью закрытыми свечами. Последняя свеча (за текущую минуту) постоянно обновляется.
- **Таблица `"TrackedSymbols"`:** Стабильна, изменяется примерно раз в сутки.

### 4.3. GitHub Actions
- Пайплайн запускается **только при `git push`** в основную ветку и должен завершаться успешно.

**Итог:** Система работает как хорошо отлаженный, автономный механизм, не требующий ручного вмешательства.
