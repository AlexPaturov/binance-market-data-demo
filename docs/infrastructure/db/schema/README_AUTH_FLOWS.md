# BinanceDataCollector — Auth Flows

## Пункт 2. Потоки и правила (Normal / Degraded / Recovery)

> Документ описывает **поведение системы** при аутентификации и авторизации.
> Привязан к схеме данных из `README_AUTH_SCHEMA.md`.

---

## 0. Термины

* **IdP** — Azure AD B2C
* **Primary authentication** — интерактивная аутентификация через IdP
* **Session / Token** — ранее выданная серверная сессия или cookie
* **Authorization Snapshot** — server-side кеш прав пользователя
* **State** — глобальное состояние системы (S0 / S1 / S2)

---

## 1. Normal Flow (S0 — Normal)

### Условия

* IdP доступен (`IDP_AVAILABLE = true`)
* `AUTH_MODE = S0`

### Последовательность

1. Пользователь инициирует вход (Sign in).
2. Происходит интерактивная аутентификация через IdP.
3. Система получает `ExternalSubjectId`.
4. Выполняется сопоставление с `UserIdentity`.

    * если отсутствует — создаётся новая идентичность и User (если разрешено политикой).
5. Загружаются роли и permissions для `User`.
6. Создаётся `AuthorizationSnapshot` со `state = authoritative`.
7. Устанавливается серверная сессия.

### Enforcement

* Все проверки прав выполняются **строго** по snapshot.
* При изменении ролей — новый snapshot создаётся при следующем refresh.

---

## 2. Degraded Flow (S1 — Degraded)

### Условия

* IdP недоступен (`IDP_AVAILABLE = false`)
* `AUTH_MODE = S1`

### Разрешено

* Использование **существующих сессий и ранее выданных токенов**.
* Восстановление UI после перезагрузки страницы.

### Запрещено

* **Первичная аутентификация** через IdP.
* Любые флоу, требующие прямого обращения к IdP:

    * interactive login
    * authorization code exchange
    * signup

### Последовательность (для активной сессии)

1. Пользователь делает запрос с существующей сессией.
2. Система читает последний `AuthorizationSnapshot`.
3. Snapshot помечается/используется как `state = stale`.
4. Проверки прав выполняются по `stale` snapshot.

### Правила

* Отзыв ролей/прав на стороне IdP **временно игнорируется**.
* Пользователь **не выкидывается** и **не блокируется**.
* Это осознанный режим **fail-open**.

---

## 3. Emergency Flow (S2 — Emergency)

### Условия

* IdP недоступен
* `AUTH_MODE = S2` (включён вручную оператором)

### Поведение пользователей

* Идентично S1 (Degraded):

    * существующие сессии работают
    * первичный login запрещён

### Дополнительно

* Доступен **Local Auth (break-glass)**
* Только для operator accounts
* Только для административных операций

### Ограничения

* Local Auth **не** используется для клиентов
* Не создаёт пользовательские сессии для внешних пользователей

---

## 4. Recovery Flow (возврат к S0)

### Условия

* IdP снова стабильно доступен
* `IDP_AVAILABLE = true`

### Последовательность

1. Система фиксирует доступность IdP.
2. Глобальное состояние переводится в `AUTH_MODE = S0` **с задержкой**.
3. **Массовый refresh НЕ выполняется**.

### Refresh прав (лениво)

* При пользовательской активности:

    1. Проверяется snapshot.
    2. Если snapshot `stale` — выполняется refresh с IdP.
    3. Применяются:

        * backoff
        * jitter
        * глобальный rate limit

### Enforcement после refresh

* Если пользователь **утратил права**:

    * snapshot обновляется
    * сессия инвалидируется
* До refresh пользователь может временно продолжать работу.

---

## 5. Thundering Herd Protection

Для предотвращения перегрузки IdP:

* refresh выполняется **по требованию**, а не массово
* используется случайная задержка (jitter)
* ограничение количества refresh в единицу времени
* при превышении лимитов используется stale snapshot

---

## 6. Аудит и наблюдаемость

Логируются события:

* LOGIN_SUCCESS / LOGIN_BLOCKED
* AUTH_MODE_CHANGED (S0/S1/S2)
* SNAPSHOT_REFRESH_SUCCESS / FAILED
* LOCAL_AUTH_USED

Все события фиксируются в `AuditEvent` и отправляются в централизованные логи.

---

## 7. Инварианты (обязательные правила)

* Emergency ≠ Local Auth
* Degraded ≠ новый логин
* Grace-сессии ≠ fallback аутентификация
* External IdP можно заменить без изменения модели прав
