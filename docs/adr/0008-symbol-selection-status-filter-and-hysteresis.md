# 0008. Отбор пар: фильтр по статусу торгов и гистерезис при снятии

**Статус:** Accepted (2026-07-13)

## Контекст

Список собираемых пар формирует `MarketScreener`: ежедневная джоба `update-symbols` берёт `ticker/24hr`, оставляет пары с суточным объёмом выше $10M, сортирует по объёму и пишет топ-40 в `TrackedSymbols` через `sp_update_tracked_symbols`. Воркеры собирают данные только по активным парам.

Два свойства этой схемы вскрылись на живом рынке.

**Первое: остановленные торги не видны в тикере.** У пары с остановленными торгами Binance продолжает отдавать в `ticker/24hr` замороженный объём последнего торгового дня. Проверено на `UTKUSDT`: `exchangeInfo` показывает `status = BREAK`, `bid = ask = 0`, а `quoteVolume` держится на $10.2M — порог в $10M пройден с запасом в 2%. Порог тогда проходили 29 пар при `topN = 40`, поэтому `.Take(40)` никого не отсекал, и пара попадала в отслеживаемые. Строк в `Trades`, `Ohlcv_*`, `OrderBook_Features` у неё не появлялось: подписка есть, потока нет. Флаг `isSpotTradingAllowed` для фильтрации не годится — у `UTKUSDT` он остаётся `true`.

**Второе: объём у порога колеблется.** У пары вблизи $10M суточный объём переходит границу туда-обратно день ото дня. Прежняя `sp_update_tracked_symbols` ставила `IsActive = FALSE` любой паре, отсутствующей в текущем скане. Значит, пара, просевшая под порог на один день, немедленно теряла сбор — до следующего попадания в ТОП. В истории образуется дыра ровно того рода, против которого строилась status-driven агрегация (ADR 0004).

## Решение

### Фильтр по `status == TRADING`

`MarketScreener.FindTopPairsAsync` дополнительно запрашивает `exchangeInfo` и пропускает только символы со статусом `Trading`. Тикер отвечает на вопрос «сколько наторговали», статус — «торгуется ли пара сейчас»; для отбора нужны оба.

Стоимость — один дополнительный REST-запрос в сутки.

### Гистерезис при снятии пары

В `TrackedSymbols` добавлена колонка `MissedScans`. `sp_update_tracked_symbols(p_symbols, p_max_missed_scans INT DEFAULT 3)`:

- пара отсутствует в скане → `MissedScans + 1`; `IsActive = FALSE` только когда счётчик достиг порога;
- пара есть в скане → `IsActive = TRUE`, `MissedScans = 0`.

Пропуски должны идти **подряд**: одно попадание в ТОП обнуляет счётчик. Скан ежедневный, порог `3` — трёхдневное окно терпимости к колебаниям объёма.

Порог — параметр процедуры со значением по умолчанию, а не константа в теле.

## Последствия

- В `TrackedSymbols` попадают только реально торгуемые пары; мёртвых подписок без единой строки данных не возникает.
- Пара у границы отбора продолжает собираться, пока не выпадет из ТОПа на три скана подряд, — сбор перестаёт рваться на суточных колебаниях объёма.
- Снятие пары запаздывает на срок до трёх суток: пара, ушедшая с рынка навсегда, ещё три дня числится активной. Цена — три дня пустой подписки, что дёшево по сравнению с дырой в истории.
- Миграция `005_tracked_symbols_hysteresis.sql` **удаляет** старую однопараметрическую функцию и создаёт новую: если оставить обе, вызов с одним аргументом (а именно так зовёт репозиторий) станет неоднозначным для Postgres.

## Отвергнутые альтернативы

**Фильтровать по `bid = ask = 0` вместо `exchangeInfo`.** Нулевые котировки у остановленной пары действительно видны прямо в тикере, и лишний запрос не нужен. Отвергнуто: это признак-следствие, а не статус. Пустая книга бывает и мгновенным состоянием живого рынка, а `status` — прямой ответ биржи на нужный вопрос.

**Задрать порог объёма вместо гистерезиса.** Подняв планку до $20–30M, можно отодвинуть колеблющиеся пары от границы. Отвергнуто: порог всё равно останется границей, около которой кто-то будет мигать, — задача просто переедет к другому набору пар, а ликвидные пары второго эшелона потеряются.

**Оставлять снятую пару активной, пока по ней идут сделки.** Отвергнуто как неограниченное: пара, навсегда выпавшая из ТОПа, но сохранившая вялый поток тиков, осталась бы в сборе бессрочно и никогда бы не освободила место.
