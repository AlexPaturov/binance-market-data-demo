# 0003. Модель очередей Hangfire с двумя серверами

**Статус:** Accepted

## Контекст

Фоновые задачи сильно разнородны по приоритету и длительности: быстрый аудит свежих данных должен отрабатывать почти мгновенно, а массовый импорт годовых архивов занимает часы. Если пустить их в одну очередь, долгие задачи забьют воркеров и заблокируют приоритетные.

## Решение

В `src/BinanceDataCollector.Worker/Program.cs` поднимаются **два Hangfire-сервера**, каждый слушает только свой набор очередей:

- **`PriorityServer`** → очереди `data_quality`, `realtime`, `quick_audit`, `maintenance` — быстрые приоритетные задачи (порядок = приоритет: `data_quality` первой, `maintenance` последней).
- **`BackgroundServer`** → очереди `historical_audit`, `archive_import`, `default` — долгие фоновые задачи.

Задачи привязаны к очередям атрибутом `[Queue("...")]` на методах воркеров (например, `[Queue("archive_import")]` на распаковке архивов, `[Queue("quick_audit")]` на быстром аудите). Порядок очередей в списке сервера задаёт приоритет их разбора.

### Что считается приоритетным (уточнение от 2026-07-13)

> **Обновление (2026-07-16, [ADR 0010](./0010-event-driven-aggregation.md)):** агрегация свечей и расчёт индикаторов больше не Hangfire-джобы, а событийные сервисы (LISTEN/NOTIFY), и в очередях Hangfire их нет. Рассуждение ниже сохранено как контекст решения; сейчас на `PriorityServer` из конвейера остаётся сбор, из обслуживания — очередь `maintenance` (ротация партиций), плюс очередь `data_quality` — оператор-триггерные проверки качества, вынесенные сюда (первой очередью), чтобы не голодать за импортом архивов на `BackgroundServer`.

**Конвейер реального времени целиком живёт на `PriorityServer`:** сбор → агрегация свечей (`OhlcvAggregatorWorker`) → расчёт индикаторов (`FeatureCalculatorWorker`). Обе задачи стоят в очереди `realtime`.

Причина — инцидент 13.07.2026. Агрегатор был помечен `[Queue("historical_audit")]`, расчёт фич — `[Queue("default")]`, то есть обе очереди обслуживал `BackgroundServer`. Запуск импорта архивов занял все 8 его воркеров пачкой `UnpackArchiveAsync` (4413 джоб) и `ImportFromCsvAsync`, и конвейер встал: свечи отстали на 3.5 часа, индикаторы — на 6, при том что `PriorityServer` простаивал. Тиковый сбор при этом шёл нормально — он не через Hangfire, — так что данные не потерялись, но всё производное от них замерло.

Критерий разделения: **на фоновый сервер идёт то, чьё опоздание никого не блокирует** (импорт архивов, глубокий аудит истории, обслуживание партиций, проверки качества). Всё, что должно поспевать за потоком тиков, — на приоритетный.

## Последствия

- Долгий импорт архивов физически не может занять воркеров приоритетного сервера — быстрый аудит, агрегация свечей и расчёт индикаторов не голодают.
- Приоритет и параллелизм настраиваются раздельно (`WorkerCount` на каждый сервер).
- Разнесение по очередям — ответственность разработчика: новую задачу нужно осознанно пометить `[Queue(...)]`, иначе она уйдёт в `default`, то есть на фоновый сервер со всеми его тяжёлыми соседями.

## Отвергнутая альтернатива

**Одна очередь / один сервер** — проще, но смешивает приоритеты: одна длинная пачка задач блокирует срочные. **Отдельный процесс на каждый тип задач** — избыточная операционная сложность; разделение очередей внутри одного Worker-хоста даёт нужную изоляцию дешевле.
