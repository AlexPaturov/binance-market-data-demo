# 0013 — Единый baseline схемы и автоматизация миграций

## Контекст

Схема БД жила в двух рукотворных местах: `init/02_schema.sql` (снимок для чистой БД и тестов) и `migrations/NNN_*.sql` (дельты для прода). Каждую правку копировали в оба, ничто не сверяло сходимость → тесты могли быть зелёными на схеме, которой нет на проде. Применённые миграции нигде не учитывались («прод на 016» держалось в памяти), накат шёл руками (`scp` + `psql`).

## Решение

Один рукотворный источник — **миграция**. Снимок baseline генерируется, руками не правится.

- **`init/02_baseline.sql`** — канонический `pg_dump --schema-only` (+ таблица `schema_migrations` с сидом свёрнутых версий). Грузится на чистом томе и во всех тестах. Цифра `02` — порядок в `docker-entrypoint-initdb.d`, не версия.
- **`schema_migrations`** (`Version`/`AppliedAt`/`Checksum`) в самой БД — что уже накатано на эту БД.
- **`migrate.sh`** — идемпотентный раннер: применяет только версии, которых нет в журнале цели, с `lock_timeout`/`statement_timeout`. Одна команда безопасна на проде, dev и в тестах.
- **`regen-schema.sh`** — свёртка: baseline + активные миграции → `pg_dump` → новый baseline, файлы уходят в `migrations/archive/`. Единственный способ обновить снимок.
- **CI-страж** (`check-schema-drift.sh` в `build-and-test`): `baseline + активные миграции == baseline`? Нет → красный «миграция уехала вперёд baseline». Несвёрнутое на прод не проходит.
- **Накат на прод** — отдельный workflow `migrate.yml` по кнопке (`workflow_dispatch`, ввод `APPLY`), независимо от деплоя кода.

Рабочий цикл: пишешь миграцию в `migrations/` → `regen-schema.sh` → коммит (миграция уезжает в `archive/`, baseline обновлён) → CI-страж зелёный → `migrate.yml` на прод по кнопке.

## Последствия

- «Два места руками» → одно (миграция) + генерируемый снимок; забыть свёртку не даёт страж (сверяет содержимое схемы дифом, а не наличие файла).
- Прод / dev / тесты строят схему одним `migrate.sh`; учёт применённого — в `schema_migrations`.
- Тяжёлые миграции остаются под ручным триггером: обрыв живого конвейера превращается в аборт по `lock_timeout`, а не в зависание.

## Отвергнутые альтернативы

- **Полный автонакат на push.** На одноузловом проде без реплики миграция «не вовремя» (rewrite `Trades`, `SET TABLESPACE` минутами) роняет живой конвейер. Оставлен ручной триггер с предохранителями.
- **Страж «есть файл миграции → красный».** Проверял бы уборку файла, а не факт свёртки: удалил файл без `regen-schema` — дрейф незаметен. Страж сверяет схему.
- **Миграции с нуля (выбросить `02_baseline.sql`, проигрывать все на каждом init).** Медленнее и требует самодостаточности миграций от пустой БД; снимок дешевле и уже есть.
