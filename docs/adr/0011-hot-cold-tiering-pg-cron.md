# 0011. Горячий/холодный тиринг дисков и эвакуация через pg_cron

**Статус:** Accepted (2026-07-17)

## Контекст

Вся БД лежала на внешнем 3.6 ТБ USB-HDD. Конвейер живёт **случайным доступом** — агрегация читает тики минут `LATERAL`-сканом, расчёт фич ходит по свечам, — и его цена это IOPS, а не полоса. Замер под импортом архивов: `%util` диска 84–89 при 16–21 МБ/с, очередь запросов 15, `iowait` 74%. Шпиндель насыщен позиционированием головки, ядра простаивают в ожидании ввода-вывода. Импорт, агрегация и расчёт фич дрались за одну головку, и никакая модель обработки эту гонку не выигрывала — узкое место физическое.

При этом на сервере был незанятый внутренний **SATA SSD** (десятки тысяч IOPS против ~200 у шпинделя) — класс устройства ровно под профиль случайного доступа.

## Решение

Данные разложены по силе дисков.

**PGDATA — на SSD.** Каталоги, WAL и активные партиции переехали на внутренний SSD: случайный доступ конвейера получает IOPS.

**Закрытые месяцы `Trades` — на HDD.** Табличное пространство `cold` на внешнем диске; `sp_evacuate_next_cold_partition()` переносит туда старейший закрытый месяц (`ALTER TABLE ... SET TABLESPACE`, индексы отдельно) одним последовательным копированием — единственной нагрузкой, в которой HDD хорош. Свечи и индикаторы остаются на SSD навсегда: они на три порядка меньше тиков, по ним ходят график и ML-выборки. Что именно значит «месяц закрыт», определяет [ADR 0012](./0012-month-seal-coverage-journal.md): печать `MonthSeal` из журнала покрытия.

**Планирует эвакуацию сама БД через `pg_cron`, а не приложение.** Раз в час `cron.schedule('evacuate-cold-partitions', ...)`. Наложение (копия месяца дольше часового тика) гасит `pg_try_advisory_xact_lock` внутри функции. Ни Hangfire-задачи, ни удерживаемого приложением соединения, ни искусственного командного таймаута — прежняя Hangfire-версия эвакуации несла таймаут 3600 с и на большом месяце под конкурентным импортом откатывала ~85 ГБ скопированного впустую.

**База пересоздана на образе `postgres:16` (Debian) + `postgresql-16-cron` с коллацией `C.UTF-8`.** pg_cron нет в alpine-образе, а смена базы alpine→Debian безопасна **только на чистой инициализации**: старая БД была `en_US.utf8`/libc, и musl→glibc сменил бы порядок сравнения текстовых индексов (`Symbol`) — тихая потеря строк при индексных сканах. Раз БД всё равно сносили под чистый датасет, коллация переведена на `C.UTF-8` (байтовый порядок, одинаковый на любой libc): текстовые индексы больше не привязаны к образу.

## Последствия

- Слив очереди агрегации вырос с ~600 до ~19 000 минут/мин, лаг свечи упал до физического минимума (~60 с), `iowait` с 74% до ~8% — ядра заняты счётом, а не ожиданием диска.
- SSD держит только активные месяцы; закрытые уезжают на HDD по мере готовности, освобождая свои десятки-сотни гигабайт.
- Отключён внешний диск — свежие данные работают, запросы за эвакуированные периоды падают с ошибкой `undefined_file` (partition pruning не пускает туда запросы за недавние даты).
- Появились инфраструктурные зависимости: собственный образ БД (`docker/postgres/Dockerfile`), `shared_preload_libraries=pg_cron`, каталог `cold` с владельцем uid postgres. Эвакуация теперь вне наблюдаемости Hangfire — её видно в логах Postgres и по размещению партиций (`pg_tablespace`).
- База стала переносимой между образами: `C.UTF-8` снимает привязку индексов к libc.

## Отвергнутые альтернативы

**Оставить эвакуацию в Hangfire, только убрать таймаут.** Убирало холостые откаты, но сохраняло лишний слой (задача, пул воркеров, удерживаемое соединение) для операции «раз в месяц» и требовало следить, чтобы обслуживание не голодало за импортом. Перенос в БД убирает приложение из пути данных совсем.

**Тонкий сайдкар-контейнер, дёргающий SQL по расписанию.** Достигал тех же целей без pg_cron и рестарта, но добавлял деплой-единицу, свои креды и мониторинг; планировщик жил бы вне БД. Для «данные двигает сама БД» pg_cron чище.

**Смена базы на Debian без пересоздания.** Отвергнута: `en_US.utf8` под glibc даёт иной порядок сравнения, чем под musl, → повреждение существующих btree-индексов по `Symbol`. Безопасно только на чистом `initdb`.

**Контроль CPU у переносчика (взять не более 10–20%).** Отвергнут как нерелевантный: `SET TABLESPACE` — последовательное копирование, оно упирается в полосу записи диска, а не в CPU. После тиринга импорт пишет на SSD, эвакуация — на почти простаивающий HDD, и реальная контенция мала; рычаг при необходимости — расписание, не CPU.
