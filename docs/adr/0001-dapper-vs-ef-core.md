# 0001. Dapper + хранимые процедуры вместо EF Core

**Статус:** Accepted

## Контекст

Основная нагрузка проекта — не CRUD, а массовая вставка тиковых данных и тяжёлая обработка на стороне БД: агрегация сделок в свечи, расчёт признаков, поиск пропусков. Объёмы измеряются сотнями миллионов строк, вставка идёт пакетами по десяткам тысяч записей.

## Решение

Доступ к данным построен на **Dapper** поверх сырых SQL-запросов и **хранимых процедур PostgreSQL** (`sp_bulk_insert_trades`, `sp_aggregate_new_trades`, `sp_upsert_ohlcv_features` и др.). Логика, работающая с большими наборами строк, живёт в БД и вызывается одним запросом; репозитории (`src/BinanceDataCollector.Infrastructure/Persistence/Repositories/`) остаются тонкими адаптерами.

Пример: `TradeRepository.BulkInsertAsync` передаёт данные в процедуру массивами-параметрами и вставляет их одним `SELECT sp_bulk_insert_trades(...)` с `UNNEST`, а не построчно через change-tracker.

## Последствия

- Массовая вставка и агрегация выполняются на стороне БД без материализации графов сущностей и без overhead'а change-tracking.
- Полный контроль над SQL: `ON CONFLICT DO NOTHING`, оконные функции, `UNNEST`, партиционирование используются напрямую.
- Цена — SQL пишется и поддерживается вручную, нет декларативных миграций из коробки (схема фиксируется отдельным baseline, см. [0006](./0006-trades-monthly-partitioning.md) и `docs/common/03_database.md`).

## Отвергнутая альтернатива

**EF Core.** Для доменной модели такого объёма change-tracking и генерация SQL стали бы узким местом на массовой вставке, а ключевые операции (агрегация, upsert признаков) всё равно пришлось бы выносить в сырой SQL/процедуры. Выгода ORM (навигации, миграции) для этого профиля нагрузки не окупается.
