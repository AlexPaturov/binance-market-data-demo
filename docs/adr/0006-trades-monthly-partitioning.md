# 0006. Помесячное партиционирование таблицы Trades

**Статус:** Accepted

## Контекст

`Trades` — самая крупная таблица (сотни миллионов строк за год). Запросы почти всегда идут по символу и диапазону времени, а исторический массив со временем нужно уметь ротировать (отцеплять старые периоды), не блокируя вставку свежих данных.

## Решение

`Trades` объявлена как **partitioned table** с `PARTITION BY RANGE ("TradeTime")`, партиции — помесячные (`Trades_2025_01`, `Trades_2025_02`, …). Управление партициями вынесено в хранимые процедуры:

- `sp_ensure_trades_partition(target_time)` — создаёт партицию нужного месяца, если её ещё нет; вызывается из `TradeRepository.BulkInsertAsync` перед вставкой, поэтому запись всегда попадает в существующую партицию.
- `sp_rotate_partitions()` — ротация партиций. Изначально календарная (13 месяцев), пересмотрена в [ADR 0007](./0007-size-based-retention-and-unified-partitioning.md): теперь по размеру диска, и та же помесячная сетка распространена на все растущие таблицы.

Схема фиксируется единым baseline `docker/postgres/init/02_baseline.sql` и применяется автоматически на чистом томе (см. `docs/common/03_database.md`).

## Последствия

- Запросы по времени затрагивают только релевантные партиции (partition pruning), а обслуживание истории — это операции над отдельными таблицами-партициями, а не над одной гигантской.
- Вставка самодостаточна: воркеру не нужно заранее заводить партиции — процедура делает это по требованию.
- Интеграционный тест (`tests/BinanceDataCollector.Infrastructure.Tests`) прогоняет реальный путь `sp_ensure_trades_partition` → `sp_bulk_insert_trades` на партиционированной схеме.

## Отвергнутая альтернатива

**Одна монолитная таблица с индексами** — деградирует на объёме: обслуживание (VACUUM, удаление старых данных) идёт по всей таблице и мешает вставке. **Партиционирование по символу** — число символов меняется и распределение неравномерно; диапазон по времени точнее ложится на реальный паттерн запросов и на задачу ротации истории.
