# 0005. `FOR UPDATE SKIP LOCKED` для выборки работы

**Статус:** Accepted

## Контекст

Расчёт признаков идёт порциями свечей. Нужно, чтобы параллельные циклы/воркеры не брали одну и ту же порцию дважды и не блокировали друг друга в ожидании, даже если обработка предыдущей пачки ещё идёт.

## Решение

Выборка новой работы реализована паттерном **claim** через `FOR UPDATE SKIP LOCKED` (`src/BinanceDataCollector.Infrastructure/Persistence/Repositories/OhlcvRepository.cs`): запрос отбирает пачку свечей со статусом «новые», блокирует именно эти строки и сразу переводит их в статус «в обработке» в одной операции. `SKIP LOCKED` заставляет конкурирующий запрос пропустить уже заблокированные строки и взять следующие свободные, а не ждать.

Метод `ClaimNewKlinesForProcessingAsync` — точка, которую вызывает `FeatureCalculatorWorker`, чтобы «зарезервировать» свой батч.

## Последствия

- Несколько обработчиков могут работать параллельно, разбирая непересекающиеся порции без взаимных блокировок.
- Нет гонки «взяли одно и то же»: строка достаётся ровно одному claim'у.
- Паттерн опирается на статус-колонку и корректный перевод статуса — часть контракта идемпотентности из [0004](./0004-watermarking-idempotency.md).

## Отвергнутая альтернатива

**Внешняя очередь/брокер для раздачи единиц работы** — лишняя инфраструктура, тогда как источник истины (сами свечи со статусом) уже в БД. **Обычный `FOR UPDATE` без `SKIP LOCKED`** — сериализует обработчиков: конкурент ждёт освобождения строк вместо того, чтобы взять другие, теряя параллелизм.
