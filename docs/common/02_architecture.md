# 02 — Архитектура приложения

## Подход

Модульный монолит с двумя хостами: **Worker** (сбор и обработка) и **DataManager** (веб-интерфейс и управление). Общая кодовая база разложена по слоям `Domain` → `Application` → `Infrastructure`, хосты — точки входа. Тяжёлые операции (bulk-вставка, агрегация, ротация) вынесены в хранимые процедуры PostgreSQL.

Оба приложения ходят в `market_analytics` через PgBouncer, обмениваются статусами через RabbitMQ и пишут логи в Seq. См. [ADR 0002](../adr/0002-worker-datamanager-split.md).

---

## Как система работает в норме

Данные идут **с WebSocket в реальном времени**. Импорт архивов — бутстрап истории и восстановление после долгого простоя, а не рабочий режим.

```
Binance WebSocket ──► Trades ──► Ohlcv_1min ──► Ohlcv_Features
                            (тики)      (свечи)      (индикаторы)

Binance WebSocket ──► книга в памяти ──► OrderBook_Features (фичи стакана)

Аудиторы ──► находят дыры от обрывов связи ──► докачивают тики ──► свечи пересчитываются
```

## Постоянные сервисы (`IHostedService`)

### `BinanceCollectorWorker` — сбор тиков

Подписан на WebSocket-потоки сделок по всем активным парам. Тики складываются в потокобезопасную очередь, отдельный writer-цикл раз в 2 секунды пишет накопленное пачкой (`sp_bulk_insert_trades`). При обрыве подписки переподписывается сам.

### `OrderBookCollectorWorker` — фичи стакана

Держит книгу каждой пары в памяти. Протокол «снапшот + диффы + проверка непрерывности + ресинк» реализует `BinanceSpotSymbolOrderBook` из Binance.Net — руками он не пишется. Раз в 5 секунд снимается срез, в конце минуты пишутся усреднённые фичи.

**Сырой L2 не хранится**: 190 ГБ/месяц против 0.4 ГБ у фич, и восстановить его неоткуда — архивов глубины по споту Binance не публикует. Подробности — [`03_database.md`](./03_database.md), раздел 3.5.

### `OhlcvAggregationService` и `FeatureCalculationService` — конвейер свечей и индикаторов

Событийные потребители: слушают `NOTIFY` PostgreSQL и разбирают работу по мере её появления, а не по тику расписания.

- `OhlcvAggregationService` слушает канал `dirty_minutes` (его шлёт вставка тиков) и пьёт очередь `DirtyMinutes` кусками по 1000 минут: тики → свечи, попутно CVD-дельта минуты тем же проходом;
- `FeatureCalculationService` слушает канал `candles_new` (его шлёт агрегация): свечи → RSI, MACD, CVD.

Каждый кусок — отдельная транзакция и отдельный коммит: обрыв посреди разбора не обнуляет проход. Слушатели ходят в базу **напрямую, мимо PgBouncer** (`DirectConnection`) — в transaction-режиме он не переносит регистрацию `LISTEN`. Потерянное уведомление страхует перепроверка очереди раз в 60 с. Общий контур обоих — `PgNotifyConsumer`. Пришли на смену cron-джобам `ohlcv-aggregator`/`feature-calculator` — [ADR 0010](../adr/0010-event-driven-aggregation.md).

## Периодические задачи (Hangfire)

| Джоба | Воркер | Расписание | Очередь | Что делает |
| :--- | :--- | :--- | :--- | :--- |
| `update-symbols` | `SymbolUpdateWorker` | раз в день | `realtime` | Сканирует рынок, отбирает топ-40 ликвидных торгуемых (`status = TRADING`) пар в `TrackedSymbols` |
| `quick_audit` | `QuickAuditorWorker` | раз в 10 минут | `quick_audit` | Дыры за последние 24 часа — то, что оставляет обрыв связи |
| `historical-audit` | `HistoricalAuditorWorker` | раз в 6 часов | `historical_audit` | Глубокая проверка истории на пропуски |
| `audit-initializer` | `AuditInitializationWorker` | раз в день | `default` | Вотермарки аудита для новых символов |
| `partition-maintenance` | `PartitionMaintenanceWorker` | раз в день | `maintenance` | Ротация партиций по размеру диска |
| `month-seal-reconcile` | `PartitionMaintenanceWorker` | раз в час | `maintenance` | Печати закрытых месяцев `MonthSeal` — критерий эвакуации ([ADR 0012](../adr/0012-month-seal-coverage-journal.md)) |

Агрегация свечей и расчёт индикаторов **в этой таблице отсутствуют намеренно**: у них поводом служит появление работы, а не время, — их ведут событийные сервисы выше. Сам физический переезд закрытых месяцев на холодный диск планирует БД через `pg_cron` (см. [`03_database.md`](./03_database.md)), вне Hangfire; в Hangfire остаётся лишь решение «месяц закрыт» (`month-seal-reconcile`) — оно требует знания очереди импорта.

Очереди разнесены по двум серверам Hangfire: `data_quality`, `realtime`, `quick_audit` и `maintenance` разбирает `PriorityServer`, остальные (`historical_audit`, `archive_import`, `default`) — `BackgroundServer`. Порядок очередей внутри сервера = приоритет: `data_quality` первой, чтобы оператор-триггерная проверка стартовала сразу, а не ждала импорт архивов на фоновом сервере; обслуживание партиций (`maintenance`) — последней, чтобы не вытеснять живую работу. Импорт архивов на `PriorityServer` не попадает вовсе — [ADR 0003](../adr/0003-hangfire-queue-model.md).

## Задачи по требованию

Запускаются вручную из DataManager, в расписании не стоят.

| Воркер | Откуда | Что делает |
| :--- | :--- | :--- |
| `ArchiveDownloaderWorker` → `ArchiveUnpackerWorker` → `CsvImportWorker` | страница **Archive** | Цепочка: скачать ZIP → распаковать → импортировать CSV в `Trades`. Скачивание и распаковка — раздельные ручные шаги (кнопки Download и Process); распаковщик сам ставит импорт следующим шагом и удаляет ZIP. Распаковка и импорт — на одной очереди `archive_import` (общий приоритет, `[Queue]` на интерфейсе `IArchiveUnpackerWorker`), иначе распаковка голодала бы за импортом. Импорт пишет покрытие в `ArchiveImportLog` — ground truth для критерия закрытого месяца ([ADR 0012](../adr/0012-month-seal-coverage-journal.md)). |
| `ArchiveDeletionWorker` | страница **Archive** | Удалить скачанные архивы |
| `DataQualityCheckWorker` | страница **Data Quality** | 23 проверки качества данных в 4 группах |
| `FillGapWorker`, `OnlineArchiveImportWorker` | ставятся аудиторами | Закрытие найденных дыр |

## Ключевое свойство: порядок прихода данных не важен

Агрегация свечей идёт **от очереди грязных минут**, а не от позиции во времени: минуту в очередь ставит сама вставка тиков, а свеча пересчитывается целиком из всех тиков минуты.

Поэтому докачанная в дыру сделка **попадает** в свечу, а импорт архивов вразнобой ничего не теряет. Раньше было иначе, и агрегатор приходилось выключать на время любой загрузки. См. [ADR 0004](../adr/0004-watermarking-idempotency.md) и [ADR 0009](../adr/0009-dirty-minutes-queue.md).

## Обработка ошибок в Hangfire-воркерах

| Тип ошибки | Примеры | Поведение |
| :--- | :--- | :--- |
| **Транзиентная** | сеть, таймаут Binance, временная недоступность БД | Retry с экспоненциальной задержкой |
| **Постоянная** | битый архив, отсутствующий файл | Fail сразу, без повторов |
| **Фатальная** | нет обязательной строки в `Processing_Watermarks` | `LogCritical` + исключение: нужна ручная починка |

`[AutomaticRetry(Attempts = 0)]` стоит там, где повтор бессмыслен или вреден, — например у `DataQualityCheckWorker` (проверка долгая, повтор её удвоит). Событийные потребители свечей и фич живут вне Hangfire: упавший кусок не роняет цикл, к нему возвращает перепроверка очереди раз в 60 с.

**Восстановление** — это и есть аудиторы: `quick_audit` закрывает дыры от коротких обрывов, `historical-audit` — от долгих простоев. Ручное вмешательство нужно, только если упала БД или сломалась схема.

## Как понять, что всё работает

**Логи (Seq):**
- `Saving N trades to the database` — тики идут;
- `Aggregated N minutes from the dirty minute queue` — свечи считаются;
- `Saved order book features for N symbols` — стакан пишется.

**База — все четыре растут:**
```sql
SELECT (SELECT count(*) FROM "Trades")             AS ticks,
       (SELECT count(*) FROM "Ohlcv_1min")         AS candles,
       (SELECT count(*) FROM "Ohlcv_Features")     AS features,
       (SELECT count(*) FROM "OrderBook_Features") AS orderbook;
```

**Отставание агрегатора:**
```sql
SELECT count(*) FROM "DirtyMinutes";
```
Десятки минут (по одной на активную пару) — норма. Сотни тысяч — идёт разбор хвоста после импорта архивов.
