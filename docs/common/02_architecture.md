# 02 — Архитектура приложения

## Подход

Модульный монолит с двумя хостами: **Worker** (сбор и обработка) и **DataManager** (веб-интерфейс и управление). Общая кодовая база разложена по слоям `Domain` → `Application` → `Infrastructure`, хосты — точки входа. Тяжёлые операции (bulk-вставка, агрегация, ротация) вынесены в хранимые процедуры PostgreSQL.

Оба приложения ходят в `market_analytics` через PgBouncer, обмениваются статусами через RabbitMQ и пишут логи в Seq. См. [ADR 0002](../adr/0002-worker-datamanager-split.md).

---

## Как система работает в норме

Данные идут **с WebSocket в реальном времени**. Импорт архивов — бутстрап истории и восстановление после долгого простоя, а не рабочий режим.

```
Binance WebSocket ──► Trades ──► Ohlcv_1min ──► Ohlcv_Features
                            (тики)      (свечи)      (индикаторы)

Binance WebSocket ──► книга в памяти ──► OrderBook_Features (фичи стакана)

Аудиторы ──► находят дыры от обрывов связи ──► докачивают тики ──► свечи пересчитываются
```

## Постоянные сервисы (`IHostedService`)

### `BinanceCollectorWorker` — сбор тиков

Подписан на WebSocket-потоки сделок по всем активным парам. Тики складываются в потокобезопасную очередь, отдельный writer-цикл раз в 2 секунды пишет накопленное пачкой (`sp_bulk_insert_trades`). При обрыве подписки переподписывается сам.

### `OrderBookCollectorWorker` — фичи стакана

Держит книгу каждой пары в памяти. Протокол «снапшот + диффы + проверка непрерывности + ресинк» реализует `BinanceSpotSymbolOrderBook` из Binance.Net — руками он не пишется. Раз в 5 секунд снимается срез, в конце минуты пишутся усреднённые фичи.

**Сырой L2 не хранится**: 190 ГБ/месяц против 0.4 ГБ у фич, и восстановить его неоткуда — архивов глубины по споту Binance не публикует. Подробности — [`03_database.md`](./03_database.md), раздел 3.5.

## Периодические задачи (Hangfire)

| Джоба | Воркер | Расписание | Что делает |
| :--- | :--- | :--- | :--- |
| `update-symbols` | `SymbolUpdateWorker` | раз в день | Сканирует рынок, отбирает топ-40 ликвидных пар в `TrackedSymbols` |
| `ohlcv-aggregator` | `OhlcvAggregatorWorker` | раз в минуту | Тики → минутные свечи |
| `feature-calculator` | `FeatureCalculatorWorker` | раз в 2 минуты | Свечи → RSI, MACD, CVD |
| `quick_audit` | `QuickAuditorWorker` | раз в 10 минут | Дыры за последние 24 часа — то, что оставляет обрыв связи |
| `historical-audit` | `HistoricalAuditorWorker` | раз в 6 часов | Глубокая проверка истории на пропуски |
| `audit-initializer` | `AuditInitializationWorker` | раз в день | Вотермарки аудита для новых символов |
| `partition-maintenance` | `PartitionMaintenanceWorker` | раз в день | Ротация партиций по размеру диска |

Очереди разнесены по двум серверам Hangfire, чтобы тяжёлая история не блокировала быстрые задачи — [ADR 0003](../adr/0003-hangfire-queue-model.md).

## Задачи по требованию

Запускаются вручную из DataManager, в расписании не стоят.

| Воркер | Откуда | Что делает |
| :--- | :--- | :--- |
| `ArchiveDownloaderWorker` → `ArchiveUnpackerWorker` → `CsvImportWorker` | страница **Archive** | Цепочка: скачать ZIP → распаковать → импортировать CSV в `Trades` |
| `ArchiveDeletionWorker` | страница **Archive** | Удалить скачанные архивы |
| `DataQualityCheckWorker` | страница **Data Quality** | 18 проверок качества данных в 4 группах |
| `FillGapWorker`, `OnlineArchiveImportWorker` | ставятся аудиторами | Закрытие найденных дыр |

## Ключевое свойство: порядок прихода данных не важен

Агрегация свечей идёт **от статуса тиков**, а не от позиции во времени: окно начинается с самого старого необработанного тика, а свеча пересчитывается целиком из всех тиков минуты.

Поэтому докачанная в дыру сделка **попадает** в свечу, а импорт архивов вразнобой ничего не теряет. Раньше было иначе, и агрегатор приходилось выключать на время любой загрузки. См. [ADR 0004](../adr/0004-watermarking-idempotency.md).

## Обработка ошибок в Hangfire-воркерах

| Тип ошибки | Примеры | Поведение |
| :--- | :--- | :--- |
| **Транзиентная** | сеть, таймаут Binance, временная недоступность БД | Retry с экспоненциальной задержкой |
| **Постоянная** | битый архив, отсутствующий файл | Fail сразу, без повторов |
| **Фатальная** | нет обязательной строки в `Processing_Watermarks` | `LogCritical` + исключение: нужна ручная починка |

`[AutomaticRetry(Attempts = 0)]` стоит там, где повтор бессмыслен или вреден: у `DataQualityCheckWorker` (проверка долгая, повтор её удвоит) и `OhlcvAggregatorWorker` (следующий цикл через минуту всё равно подхватит).

**Восстановление** — это и есть аудиторы: `quick_audit` закрывает дыры от коротких обрывов, `historical-audit` — от долгих простоев. Ручное вмешательство нужно, только если упала БД или сломалась схема.

## Как понять, что всё работает

**Логи (Seq):**
- `Saving N trades to the database` — тики идут;
- `Aggregated N candles from unprocessed trades` — свечи считаются;
- `Saved order book features for N symbols` — стакан пишется.

**База — все четыре растут:**
```sql
SELECT (SELECT count(*) FROM "Trades")             AS ticks,
       (SELECT count(*) FROM "Ohlcv_1min")         AS candles,
       (SELECT count(*) FROM "Ohlcv_Features")     AS features,
       (SELECT count(*) FROM "OrderBook_Features") AS orderbook;
```

**Отставание агрегатора:**
```sql
SELECT count(*) FROM "Trades" WHERE "ProcessingStatus" = 'new';
```
Тики последней минуты — норма. Десятки миллионов — агрегатор не справляется.
