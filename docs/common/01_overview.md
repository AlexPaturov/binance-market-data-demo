# Документация: 01 - Обзор проекта

## 1. Назначение системы

**`BinanceDataCollector`** — это автономный, самовосстанавливающийся и отказоустойчивый программный комплекс, предназначенный для непрерывного сбора и хранения рыночных данных с криптовалютной биржи **Binance**.

Основная задача системы — формировать чистое, полное и готовое к анализу хранилище данных, которое может служить фундаментом для:
- Бэктестинга торговых стратегий.
- Расчета технических индикаторов.
- Машинного обучения и предиктивного анализа.
- Визуализации рыночной активности.

## 2. Философия и ключевые принципы

Система спроектирована с учетом следующих принципов:

- **Автономность:** После первоначальной настройки система работает 24/7 без необходимости вмешательства человека.
- **Надежность:** Все компоненты спроектированы для автоматического перезапуска и восстановления после сбоев.
- **Целостность данных:** Встроенные механизмы аудита находят и заполняют любые пробелы в данных, которые могли возникнуть из-за простоев.
- **Производительность:** "Тяжелые" операции (массовая вставка, агрегация) вынесены на уровень базы данных для максимальной эффективности.
- **Автоматизация развертывания:** Обновления кода доставляются на сервер автоматически через CI/CD пайплайн, что минимизирует риск человеческой ошибки.

## 3. Основной алгоритм работы

Система функционирует как непрерывный конвейер данных, состоящий из пяти логических этапов:

1.  **Разведка (`Scanner`):** Система периодически сканирует рынок, чтобы определить список самых ликвидных и волатильных валютных пар. Это гарантирует, что собираются только релевантные данные.
2.  **Сбор (`Collector`):** Система в реальном времени подписывается на потоки сделок (тиков) для этих отобранных пар и сохраняет каждый тик в базу данных.
3.  **Стакан (`OrderBook`):** Параллельно система держит в памяти биржевой стакан по каждой паре и раз в минуту сохраняет из него готовые фичи — дисбаланс bid/ask, ликвидность вблизи цены, спред, крупные заявки. Сырой L2 не хранится: его объём несоизмерим с ценностью, а восстановить его задним числом всё равно невозможно.
4.  **Агрегация (`Aggregator`):** Сырые тики непрерывно сворачиваются в минутные свечи (OHLCV), поверх которых считаются технические индикаторы.
5.  **Аудит (`Auditor`):** Система регулярно проверяет целостность накопленных данных. Найденные «дыры» (от обрывов связи или простоев) она автоматически заполняет из исторических архивов Binance — и свечи по этим периодам пересчитываются.

Порядок прихода данных значения не имеет: агрегация идёт от очереди грязных минут, которую наполняет сама вставка тиков, поэтому докачанная задним числом сделка попадает в свечу.

## 4. Наблюдение за данными

В `DataManager` есть биржевой график (свечи 15м–1нед, MA поверх цены, RSI / MACD / CVD отдельными панелями) и панель проверок качества данных — 18 проверок в четырёх группах, запускаются оператором по кнопке.

На главном дашборде — помесячная сводка партиций `Trades`: где физически лежит месяц (горячий SSD или холодный HDD) и запечатан ли он критерием закрытого месяца. Для незапечатанного месяца видна причина: нет импорта, дыра в покрытии, не сагрегировано или свечи не обработаны. Стоящее за этим — тиринг дисков и печать месяца, [ADR 0011](../adr/0011-hot-cold-tiering-pg-cron.md) и [ADR 0012](../adr/0012-month-seal-coverage-journal.md).

## 5. Ограничение по диску

Данные лежат на диске 3.6 ТБ. Ротация идёт **по размеру, а не по календарю**: пока занято больше порога, дропается самый старый месяц — сразу во всех таблицах. Реальный размер месяца гуляет от 32 до 148 ГБ, поэтому «держим N месяцев» ничего не говорит о том, сколько истории влезет. Ожидаемое окно — 19–30 месяцев.

## 6. Технологический стек

- **Язык / платформа:** C# / .NET 8
- **База данных:** PostgreSQL 16 (Dapper + хранимые процедуры)
- **Фоновые задачи:** Hangfire
- **Среда выполнения:** Docker
- **CI/CD:** GitHub Actions
- **ОС сервера:** Ubuntu Server
