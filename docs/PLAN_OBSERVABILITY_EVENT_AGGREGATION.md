# План: наблюдаемость + событийная агрегация

Рабочий план устранения инцидента агрегации с подтверждением метриками и тестами.
Документ для отслеживания хода работ по шагам; по завершении сворачивается в post-mortem,
а этот файл удаляется.

**Рамка:** 7 календарных дней с момента старта (поправьте, если не согласны).
Всё, что не влезло в критерий готовности к концу рамки, — режется без жалости.

---

## 1. Контекст

**Инцидент.** Агрегация свечей ушла в livelock: пачка фиксированного размера в одной
транзакции не укладывалась в командный таймаут 600 с на фоне импорта архивов, откатывалась
целиком, и таймер через минуту запускал то же самое. Прогресс — ноль, диск молотит впустую,
копии джоб копятся.

**Цепочка виновников** (класс → метод → процедура):

1. `HangfireJobsService.StartAsync` — агрегация как cron `Cron.Minutely()`: обработка
   привязана к тику таймера, а не к появлению работы.
2. `OhlcvAggregatorWorker.AggregateNextBatchAsync` — фиксированная пачка (`BatchMinutes`).
3. `TradeRepository.AggregateDirtyMinutesAsync` — `commandTimeout: 600` — стена.
4. `sp_aggregate_dirty_minutes` — вся пачка в одной транзакции: не успела → откат целиком.

Формула тупика: *фиксированная пачка × одна транзакция × внешний таймаут × таймер-перезапуск*.
Подкрутки констант (размер пачки, TTL, skip-фильтры) двигали константы внутри формулы,
не меняя её.

**Больное состояние на момент написания (15.07.2026 02:52 UTC):**
очередь `DirtyMinutes` = **1 958 891** минута, импорт архивов завершён (очередь архивов — 0),
лаг свечи ~8 мин. Болезнь ещё видна — это наше «до» для метрик.

## 2. Дыры плана и их закрытие (по итогам обсуждения)

### Дыра 1 — отсутствие границы
Латание симптомов вслепую вместо корня разрослось в шлейф дефектов (осиротевшие
флаги после рестарта, пачки-дубли, TTL-костыль) — все они мои недофиксы поверх одной
коренной проблемы. Без таймбокса такое латание съест подготовку к собеседованию.
**Закрытие:** рамка 7 дней + критерий готовности (раздел 5). Сверх критерия — полировка, режем.

### Авторство (для post-mortem и интервью)
Дефекты и предыдущие недофиксы (таймерная модель, фиксированная пачка в одной
транзакции, подпорки) — на исполнителе-агенте. **Решение о смене модели обработки с
временной на событийную — оператора** (сформулировано до развёртывания в LISTEN/NOTIFY).
На интервью это senior-сигнал от первого лица: «увидел, что точечные фиксы не сходятся,
и продавил смену модели».

### Дыра 2 — «метрики поймают баг» (пересмотрена)
Хронологически причину нашли логи и SQL — но *оператором* баг на метриках ещё не увиден,
и навык узнавания сигнатуры приобретается только глазами на живой патологии.
**Закрытие:** метод «предсказание → наблюдение → фикс → инверсия кривых».
Лист предсказаний (раздел 3) заполняется **до** установки стека. Каждое совпадение
предсказания с картинкой — подтверждение root cause; каждое расхождение — учебный материал.

### Дыра 3 — «тест, воспроизводящий баг»
Буквальное воспроизведение (600 с таймаута на прод-объёме) в CI невозможно физически.
**Закрытие:** тестируется **свойство**, сделавшее баг фатальным: «обрыв одного вызова
обнуляет весь прогресс». Такой тест красный на старой схеме и зелёный на событийной.
Нагрузочный сценарий на объёме — опциональный, вне CI, вне критерия готовности.

## 4. Этапы реализации

Состав: `prometheus` + `node_exporter` + `postgres_exporter` + `grafana`.
Кода в приложении — ноль: все прикладные числа снимаются SQL-запросами через
custom queries `postgres_exporter`.

- [x] 1.1 `prometheus`: `docker/prometheus/prometheus.yml`, named volume, retention 30 дней.
      Наружу — только Tailscale `:9091` (порт 9090 на хосте занят Cockpit).
- [x] 1.2 `node_exporter`: метрики хоста — диск (%util, iowait), CPU, память.
- [x] 1.3 **Два** `postgres_exporter` (по одному на БД) + `queries_bdc.yaml` / `queries_jobs.yaml`:
      `bdc_dirty_minutes_depth`, `bdc_candle_lag_seconds`, `bdc_feature_lag_seconds`,
      `bdc_aggregation_succeeded_15m` / `_failed_15m` / `_avg_duration_seconds` / `_max_...`,
      `bdc_hangfire_queue_depth{queue}`.
- [x] 1.4 `grafana`: на Tailscale `:3000` (не через Traefik — чтобы не зависеть от
      Cloudflare DNS для быстрого доступа); пароль админа через env `GRAFANA_ADMIN_PASSWORD`

- [x] 1.5 Дашборд «BDC — конвейер агрегации»: 3 плитки + 5 графиков (очередь, лаги,
      диск %util/iowait, успех/провал, длительность прохода с порогом 600 с).
- [x] 1.6 Один алерт (Grafana alerting): лаг свечи выше порога либо очередь растёт
      N минут подряд. **Не сделано.**
- [ ] 1.7 **Снимок больного состояния** — оператор смотрит живьём; выгрузку «до» ещё не сняли.
- [ ] 1.8 Выключить самодельный SSH-монитор из сессии агента (его заменяет стек).
      Пока работает — оставлен для непрерывности до настройки алерта (1.6).

### Этап 3 — событийная модель (исполнитель: агент; ревью: оператор)

Событие уже есть — строка в `DirtyMinutes` от вставки тиков. Меняется потребитель:
вместо cron-джобы — постоянный слушатель.

- [x] 3.1 Миграция 010: `NOTIFY dirty_minutes` в конце `sp_bulk_insert_trades`
      (только если вставилось > 0) и `NOTIFY candles_new` в конце
      `sp_aggregate_dirty_minutes` (только если пересчитано > 0).
      Обратно совместимо: старый воркер уведомления просто не слушает —
      миграция применяется до деплоя без двухфазности.
- [x] 3.2 `OhlcvAggregationService` (`BackgroundService`): `LISTEN dirty_minutes`;
      цикл — пить `sp_aggregate_dirty_minutes(малый_кусок)` до пустой очереди
      (каждый вызов = своя транзакция = свой коммит), затем ждать NOTIFY со
      страховочной перепроверкой раз в 60 с (на случай потерянного уведомления).
- [x] 3.3 `FeatureCalculationService` — тот же контур на `candles_new`
      (существующая логика `FeatureCalculatorWorker` переиспользуется).
- [x] 3.4 Демонтаж таймерной модели: recurring-джобы `ohlcv-aggregator` и
      `feature-calculator` удаляются из `HangfireJobsService` (+ `RemoveIfExists`
      при старте, чтобы вычистить прод), с этих воркеров снимаются
      `SkipWhenPreviousJobIsRunning` / `DisableConcurrentExecution` — компенсации
      таймерной модели больше не нужны. Класс `SkipWhenPreviousJobIsRunningAttribute`
      **удаляется вместе с тестами**, если других потребителей не осталось (это моя
      подпорка, а не самостоятельная ценность — оставлять её рядом с событийной
      моделью значит сохранять мусор, который снова кого-то запутает).
- [x] 3.5 Тесты устойчивости (testcontainers), «красные на старой схеме»:
      - потребитель пьёт очередь досуха, а не один глоток;
      - обрыв соединения посреди вызова → закоммиченные куски на месте,
        очередь не повреждена, следующий вызов продолжает;
      - падение одного вызова не останавливает цикл;
      - потерянный NOTIFY не подвешивает потребителя (страховочный тик).
- [~] 3.6 Деплой: **миграция 010 накачена на прод 16.07.2026 ~11:42 UTC** (уведомления
      идут, проход агрегации через подмену процедур прошёл успешно). Осталось: руками
      добавить `ConnectionStrings__DirectConnection` в `bdc_worker` (compose автодеплой
      не разносит) → push → авто-деплой воркера.
      Порядок безопасен (3.1); рестарт воркера при живом стеке метрик — само по себе
      наблюдение для П5.

## 5. Критерий готовности (Definition of Done)

Всё перечисленное — и **стоп**, дальше подготовка к собеседованию:

1. Дашборд с четырьмя графиками работает на проде.
2. Один алерт настроен и проверен (сработал на больном состоянии или тестовом пороге).
3. Событийный потребитель на проде, cron-джобы агрегации и фич удалены.
4. Очередь `DirtyMinutes` = 0, лаг свечи — секунды.
5. Тесты устойчивости зелёные в CI.
6. Post-mortem и ADR 0010 в `docs/`.

Явно **вне** критерия (по желанию, после): нагрузочный сценарий на dev-объёме,
дополнительные дашборды, Alertmanager, cadvisor, метрики из приложения.
